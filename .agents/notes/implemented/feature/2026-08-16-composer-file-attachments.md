# Agent Note: composer file attachments — paperclip intake, text-file drafts, prompt folding

Status: implemented

English | [中文](2026-08-16-composer-file-attachments.zh.md)

## Problem

The web composer accepted only images (paste and whole-page drop, per the [multimodal image input note](2026-07-22-web-multimodal-image-input-and-durable-attachments.md) and the [intake limits note](2026-08-12-web-image-intake-and-limits-alignment.md)); its README documented the leading plus button as "not an attachment surface". Attaching a source or text file to a prompt — the Codex-style gesture — had no client path at all.

## Decision

**One intake funnel behind three gestures.** A paperclip button (`input.attach`, `IconPaperclipOutline16`) beside the plus button opens a hidden `<input type="file" multiple>` with no `accept` filter — classification happens in code so a refused file gets product copy instead of a silent picker-level filter. The button, paste, and the document-level drop all feed InputBar's `intakeFiles`: `image/*` files keep the existing image path (the `imageLimits` pre-check, `createDraftImages`, preview URLs) untouched; text files — a `text/*` MIME type, an allowlisted extension, or a known dotfile name (`.gitignore`, `.env.example` style) — go through the new async `addFiles` inject callback to `ConversationController.createDraftFiles`, which enforces a fixed 256KB single-file cap, reads full content via `file.text()`, and registers the draft only once every read succeeded; anything else is announced with `file.unsupportedType` (暂不支持该类型文件) and never enters the rail. Size-cap and read failures surface as typed errors (`DraftFileTooLargeError`/`DraftFileReadError`) that the apply-layer inject maps to `file.tooLarge`/`file.readFailed` copy — the same boundary-localization pattern as `UnsupportedImageMediaTypeError`.

**One draft registry, one id slot.** `ComposerAttachment` is now a union: `{ kind: 'image', file, previewUrl }` or `{ kind: 'file', name, text }`. The input machine's `imageIds` slot tracks both kinds unchanged (no machine, facade, or hub change); ConversationController's `draftAttachments` map remains the single content store, and `releaseDraftImage` revokes a preview URL only for image kinds. The `AttachmentRail` atom renders a previewUrl-less item as a content-sized name chip with a remove control and no open affordance, so images and files interleave in draft order.

**Folding, not a new content block.** `sendSession` keeps image parts first and folds each text file into the single text part ahead of the typed draft — `文件 ${name} 的内容：\n\`\`\`\n${text}\n\`\`\`\n\n` per file, in draft order — so a files-only send is the file blocks alone. The file content therefore reaches the model as ordinary prompt text captured by the existing prompt event, satisfying the model-visible ⟺ logged rule with no new session event. Drop-overlay copy (`image.dropTitle`/`dropDesc`) no longer says images-only; the keys are unchanged.

**Office documents extract locally, parsers never ride the bundle.** The funnel's classification order is image → plain text → office (`.pdf`/`.docx`/`.xlsx`/`.pptx`, by extension) → reject. `createDraftDocuments` caps the file at 10MB (`file.tooLarge` is now size-parameterized), extracts text in the browser — pdf.js page text, mammoth raw Word text, one CSV section per Excel sheet (`# Sheet: <name>`), one `# Slide N` section per PowerPoint slide's DrawingML `a:t` runs — truncates at 200KB of UTF-8 with the `file.truncated` note appended to the folded block, and maps any loader/parser/blank-content failure to `file.parseFailed` (文档解析失败) via `DocumentParseError`. The plugin client bundle is a single CJS artifact that inlines every dependency, so the parsers (pdf.js, mammoth, SheetJS, JSZip — ~3MB combined) load as **classic scripts** from the app's `office-parsers/` assets on first use: apps/web's vite build emits them verbatim from this package's parser dependencies, and classic scripts are the one mechanism that also works over the desktop shell's file:// dist, where ESM `import()` of a URL is unavailable. pdf.js runs pinned at v3 (the last UMD build; v4+ is ESM-only); its fake-worker fallback reloads the worker script inline when the Worker constructor fails, so a broken worker degrades to slower parsing, never a broken page. Pending name chips sit beside the rail while extraction runs.

## Alternatives considered

**A separate `fileIds` slot in the input machine.** Symmetric naming, but it would have churned the machine, facade, hub, and every workspace-switch carry-over path for zero behavioral difference — the machine treats the ids as opaque ordered tokens either way. The stale `imageIds`/`addImages` names are documented in the contract JSDoc instead.

**Uploading files as durable attachments like images.** Images cross the host boundary because models consume them as bytes; a text file's content is prompt text, and folding keeps replay, fork, and the queue's text-preview machinery working with no host or wire change. A durable file-attachment block can still come later if a model-visible binary file ever needs it.

**A configurable byte cap and extension list.** The 256KB cap and the allowlist are product constants with fixed product copy (「文件过大（最大 {size}）」), matching the image intake's fixed media-type list; no deployment varies them today, so no Config field was added. The office caps (10MB file, 200KB extracted text) follow the same argument.

**Inlining the parsers with lazy execution.** `tsdown`'s `noExternal` rule inlines every non-platform dependency into the single-file CJS plugin bundle, so "lazy" `import()` would still ship ~3MB of parser code in every page load — the initial-load budget this feature exists under rules that out. Runtime ESM `import()` of a served URL was rejected on the desktop shell: Electron loads dist over file://, where module loading is blocked, while classic scripts work everywhere including the fake-worker path pdf.js needs.

**pdf.js v5 (current) instead of v3.** v4+ ships ESM-only builds; the script-tag loader needs the UMD global (`window.pdfjsLib`), so the parser is pinned at 3.11.174 — text extraction only, no rendering surface, so the older engine's rendering fixes don't apply here.

## Consequences

Non-image non-text files that previously produced the image-format rejection (e.g. a dropped PDF) now produce the unsupported-type notice — one intake announcement changed class; a later round then taught PDF (and Word/Excel/PowerPoint) a real path. The composer DOM gains a button and a hidden input, so every browser snapshot golden that captures the tool row (the ~40 `*.expected.md` aria snapshots naming the "Commands" button) churns on the next `DSH_SNAPSHOT=refresh`; the office round adds no always-on DOM beyond that. Files over their cap and unreadable or unparseable files are refused at intake with immediate copy; the host never sees them. apps/web's dist carries ~2.9MB of `office-parsers/` assets, fetched only on first office attachment. Draft file text lives only in memory: a page reload loses unattached drafts, same as image drafts. pdf.js stays on v3 until the desktop shell gains a module-capable serving protocol or the composer moves to a host-side extraction seam.
