# Agent Note: 暂存的桌面运行时按平台-架构分键，信任前先探测

Status: implemented

[English](2026-08-21-desktop-runtime-arch-keyed-staging.md) | 中文

## 问题

一位 Ubuntu x86_64 用户从 rc.33 升级到 rc.35 后，桌面壳启动即失败：受监管的子进程打印 `node: 1: ELF...: not found` / `node: 2: Syntax error: ")" unexpected` 并以退出码 2 退出。这几行是 dash 把 ELF 当脚本解释的输出——`execve` 返回 ENOEXEC 时 glibc 的 `execvp` 会回退到 `/bin/sh`，而对一个格式完好的 ELF 来说 ENOEXEC 意味着内核拒绝其机器类型：暂存的 `node-runtime/bin/node` 是一个与 CPU 架构不符的 Linux 二进制。发布产物已逐字节排除嫌疑（两个 deb 的 `md5sums` 里内置 node 的条目与官方 Node.js v22.21.1 发行包在 x64 和 arm64 上完全一致，且 AppImage 与 deb 共用同一份暂存运行时），所以外来二进制只存在于用户的数据根目录里。

[userData 暂存笔记](2026-08-16-desktop-runtime-staged-under-userdata.zh.md)当时只按应用版本给暂存副本命名，并无条件信任完成标记。home 目录在不同架构的机器间共享、同步或迁移过——或任何手工放置的副本——都会把异架构运行时钉在 `runtimes/<version>` 下，而标记文件让它在之后每次启动都生效，除了手工删目录没有任何恢复路径。

## 决策

**暂存副本按平台-架构分键，标记必须先赢得信任。** `stagePackagedRuntime` 现在暂存到 `runtimes/<version>-<platform>-<arch>`，异架构的副本永远占不了本机的槽位——而旧的纯版本目录会在首次成功暂存后作为残留被清理，受影响的安装在下次启动时无需手工干预即可自愈。

写入完成标记之前，暂存副本必须通过 `node --version` 探测。探测失败只重拷一次（覆盖瞬时拷贝故障这一类），第二次仍失败就在暂存阶段抛出带平台/架构信息的错误——跑不起来的运行时以清晰的启动错误暴露，而不是在三个进程之后变成 dash 的乱码脚本诊断。

## 备选方案

**每次启动都探测。** 连标记后的损坏也能抓到，但代价是每次启动多拉起一个子进程，而所报告的故障类已经被架构键覆盖。拒绝；稳态启动保留标记快速路径。

**对暂存树做文件清单（sha256）校验。** 完整性更强，但观察到的故障是可执行性而非位腐败；清单要维护文件列表、拉长暂存时间，针对的是一个没有现场证据的故障类。拒绝。

**保留纯版本目录、只加探测。** 在两个架构共享 home 的场景里，任一台机器的每次启动都会永动机式地重拷另一架构的副本——探测把静默变砖变成了永久空转。拒绝，改为分开槽位。

## 后果

本次改动后的首次启动会重新暂存一次运行时（新目录名）并清理旧的 `<version>` 目录。稳态启动不受影响；探测只发生在全新暂存时。行为覆盖：`apps/desktop/tests/runtime.spec.ts`（探测重试、持续探测失败拒绝、架构键复用、崩溃恢复、版本变更）。打包产物本身从未涉案——deb 与 AppImage 携带的始终是官方按架构分发的 Node.js，未做任何改动。
